# Специалист MX — эмулятор

Эмулятор радиолюбительского компьютера **«Специалист MX»**. Настольное приложение для Windows
и Linux: JavaFX-окно с экраном 384×256, Swing-отладчик, эмуляция ОЗУ, RAM-диска, ROM-диска,
клавиатуры, программируемого таймера, контроллера НГМД и динамика.

Процессор — на выбор: **КР580ВМ80А (i8080)** или **Zilog Z80**. Оба ядра реализованы в проекте,
активное выбирается из меню и запоминается в `specialist_mx.ini`.

Справка по железу — на сайте [spetsialist-mx.zx-pk.ru](https://spetsialist-mx.zx-pk.ru/index.html):
базовая машина «Специалист» и доработка до «Специалиста MX».

## Возможности

- Экран 384×256 пикселей, 1 бит на точку, 12 Кбайт видеопамяти в основной странице.
  Экранная область — `0x9000`–`0xBFFF`; байт хранит 8 горизонтальных точек, адрес байта
  `0x9000 + y*32 + x/8`.
- **Цвет.** 16 цветов на точку: младший полубайт кода цвета — цвет фона, старший — цвет
  изображения. Палитра — 8 цветов RGB, расширенных до 16 битом яркости `Y`
  ([таблица цветности ПК «Специалист MX»](https://spetsialist-mx.zx-pk.ru/index18.html)):

  | Код | Цвет       | Y | R | G | B | Код | Цвет           | Y | R | G | B |
  |-----|------------|---|---|---|---|-----|----------------|---|---|---|---|
  | 0   | чёрный     | 0 | 0 | 0 | 0 | 8   | тёмно-серый    | 1 | 0 | 0 | 0 |
  | 1   | синий      | 0 | 0 | 0 | 1 | 9   | ярко-синий     | 1 | 0 | 0 | 1 |
  | 2   | зелёный    | 0 | 0 | 1 | 0 | A   | ярко-зелёный   | 1 | 0 | 1 | 0 |
  | 3   | бирюзовый  | 0 | 0 | 1 | 1 | B   | ярко-бирюзовый | 1 | 0 | 1 | 1 |
  | 4   | красный    | 0 | 1 | 0 | 0 | C   | розовый        | 1 | 1 | 0 | 0 |
  | 5   | фиолетовый | 0 | 1 | 0 | 1 | D   | сиреневый      | 1 | 1 | 0 | 1 |
  | 6   | коричневый | 0 | 1 | 1 | 0 | E   | жёлтый         | 1 | 1 | 1 | 0 |
  | 7   | белый      | 0 | 1 | 1 | 1 | F   | ярко-белый     | 1 | 1 | 1 | 1 |

- **Ограничение цвета.** Контроллер цвета реальной машины хранит код цвета **отдельно
  для каждой 8-точечной «посылки»**: код запоминается в собственном ОЗУ цвета в момент
  записи байта в экранную память, поэтому соседние посылки и целые участки экрана могут
  иметь разные цвета. В эмуляторе ОЗУ цвета не моделируется: порт `0xFFF8` задаёт текущий
  цвет, и он применяется к тем байтам, которые программа перезаписывает. Участок, уже
  выведенный на экран, при смене цвета не перекрашивается — в отличие от реальной машины,
  где код цвета хранится в ОЗУ и сохраняется при последующих обращениях к экранной памяти.

  Конкретные значения RGB в эмуляторе (`Screen.COLORS`): у базовых кодов `0`–`7` канал
  выключенного цвета равен `0x00`, включённого — `0xFF`; для кодов `8`–`F` к каждому каналу
  добавлено по `0x20`. Исключение — код `5` (фиолетовый, `0x99_00_FF`) и код `6`
  (коричневый, `0x97_47_06`): палитра эталонной таблицы цветности показывает там именно
  такие тона, а не чистые `FF_00_FF` и `FF_FF_00`.
- Память: основная страница и до 8 страниц RAM-диска по 64 Кбайт, ROM-диск ПЗУ до 48 Кбайт.
  Подключение/отключение страниц — записью в `0xFFFC` (закрыть), `0xFFFD` (открыть RAM-диск)
  и `0xFFFE` (открыть ROM-диск).
- Клавиатура — матрица 12 столбцов × 6 строк через КР580ВВ55 (`0xFFE0`), две раскладки:
  «Специалист MX» и стандартная «Специалист».
- Программируемый таймер КР580ВИ53 (`0xFFEC`), порт программирования (`0xFFE4`).
- Контроллер НГМД КР1818ВГ93 (`0xFFE8`, порт `0xFFF0`), образы дисков `.odi`.
- Динамик, подключённый к таймеру.
- Переключение процессора i8080 ↔ Z80 без потери состояния: общие регистры (`AF`, `BC`, `DE`,
  `HL`, `SP`, `PC`) переносятся на новый процессор, поэтому программа, совместимая с обоими,
  продолжается с того же места.
- Отладчик (Swing) для любого из двух процессоров: регистры, флаги, дизассемблер, точки останова,
  шаг, шаг через вызов, «Run to cursor», поиск данных, просмотр и правка памяти.

## Форматы файлов

| Формат | Что это                                            | Как загружается                                                         |
|--------|----------------------------------------------------|-------------------------------------------------------------------------|
| `.rom` | ПЗУ/монитор целиком                                | «Файл → Открыть», загружается с адреса `0x0000` и запускается           |
| `.mon` | Монитор; адрес загрузки берётся из имени `nm_addr` | Автоматически при запуске `.cpu`, если монитор не тот, что нужен        |
| `.cpu` | Текстовый заголовок + данные `.i80`                | Диалог с адресами загрузки и старта, выбор «запустить/только загрузить» |
| `.rks` | Бинарный формат с заголовком и контрольной суммой  | «Файл → Открыть»                                                        |
| `.odi` | Образ дискеты                                      | «Файл → Диск A / Диск B»                                                |

Блок памяти сохраняется в `.cpu` (текстовый заголовок + `.i80`) и `.rks` через «Файл → Сохранить блок...».

## Настройки

Файл `specialist_mx.ini` в каталоге приложения, секция `[Config]`:

| Опция              | Смысл                                 |
|--------------------|---------------------------------------|
| `RomFile`          | ROM-файл, открытый при старте         |
| `Cpu`              | Активный процессор: `i8080` или `Z80` |
| `MainFormWidth`    | Ширина главного окна                  |
| `MainFormHeight`   | Высота главного окна                  |
| `DebugFrameWidth`  | Ширина окна отладчика                 |
| `DebugFrameHeight` | Высота окна отладчика                 |

Отсутствующее или неизвестное значение `Cpu` трактуется как `i8080`.

автоматически по записи в `0xFFFD`, ROM-диск — по `0xFFFE`; общий порт `0xFFFC` закрывает
страничные диски.

## Процессор i8080

Реализован документированный набор КР580ВМ80А; недокументированные коды ведут себя как их
документированные аналоги, но дизассемблер показывает их в нижнем регистре (`jmp`, `call`, `ret`).
Регистр `F` маскируется при записи через регистровую пару — биты, которые у i8080 всегда
равны 0 или 1, не сохраняются.

## Процессор Z80

Реализован полный набор команд Zilog **NMOS Z80** (Z0840004), включая недокументированные
команды и недокументированные флаги:

- наборы `CB`, `ED`, `DD`/`FD`, составные `DD CB d op` / `FD CB d op`;
- недокументированные `SLL`, обращение к половинам индексных регистров `IXH/IXL/IYH/IYL`
  (в том числе в `LD` и арифметико-логических командах), `IN F,(C)`, `OUT (C),0`;
- пара альтернативных регистров (`EX AF,AF'`, `EXX`);
- внутренний регистр `MEMPTR` (`WZ`) и регистр `Q` — от них зависят недокументированные
  флаги `F5`/`F3` и поведение `SCF`/`CCF`.

Недокументированные флаги вычисляются по правилам «The Undocumented Z80 Documented» и справочной
таблицы флагов z80.info, а не копируются из результата: у 8-битной арифметики и `BIT n,r` они
берутся из операнда, у 16-битной — из старшего байта результата, у блочных команд — из внутренней
операции, у `LD A,I`/`LD A,R` — из аккумулятора.

**Что сознательно не реализовано:** режимы прерываний `IM 0`/`IM 1`/`IM 2` и вход `INT`/`NMI`.
Процессор в эмуляторе прерывания не принимает; коды `ED` для `IM` выполняются как `NOP`
длиной два байта. Регистры `I` и `R` обслуживаются (`LD A,I`, `LD A,R`, `LD I,A`, `LD R,A`,
инкремент `R` на выборке байта команды), но прерывания по ним не формируются.

**Почему прерываний нет на этой машине.** `IM 0`/`IM 1`/`IM 2` — это способ реакции процессора
на уже пришедший сигнал `/INT`, а не источник прерывания. На «Специалисте MX» линия `/INT`
не разведена: единственный потенциальный источник, выход `OUT` таймера КР580ВИ53, подключён
к динамику (см. `ProgrammableTimer`), а не к процессору. Входа `/NMI` это тоже касается —
его никто не дёргает. Поэтому ни i8080, ни Z80 на MX прерываний не получают; разница между
ними только в том, что Z80 умел бы на них реагировать, если бы провод был. `RST n` — это
не прерывание, а вызов подпрограммы, и он реализован.

**Отличие регистра `F` от i8080.** Бит 2 у Z80 — это `P/V` (переполнение при арифметике,
чётность при логических и блочных командах), тогда как у i8080 тот же бит — только чётность.
Биты 5 и 3 — `F5`/`F3`, бит 1 — `N`. Следствие: программа для i8080, проверяющая `PE`/`PO`
после арифметики, на Z80 получит другое условие перехода — это документированное поведение Z80,
а не ошибка реализации.

## Как проверяется точность процессоров

- `zexdoc` и `zexall` (Z80 instruction exerciser, Frank Cringle) — прогон десятков тысяч
  комбинаций операндов по каждой команде со сверкой CRC состояния с эталонным Z80.
  `zexdoc` сверяет документированные флаги, `zexall` — ещё и недокументированные. **Важно:**
  `zexall` маскирует флаги константой `0D7h`, поэтому биты `F5`/`F3` он **не проверяет**.
- `z80type` (Sergey Kiselev) — определение типа Z80 по поведению `F5`/`F3` в `SCF`/`CCF`,
  наличию `OUT (C),0` и команды `MLT BC` (`ED 4C`). Эталонный результат для NMOS Z80:
  `XF/YF: FF`, `XF/YF flags test: C000C000`, `Detected CPU type: Zilog Z80, Zilog Z08400 or similar NMOS CPU`.
- `8080PRE`, `TST8080`, `CPUTEST`, `8080EXER` — стандартные exerciser'ы для i8080.

## Сборка

Требуется JDK 8 (с JavaFX, если собираете под Linux) и Maven.

```bash
mvn -DskipTests clean package
```

Готовый JAR — `target/specialist_mx-2.0.0.jar` (shade-plugin собирает все зависимости внутрь),
под Windows дополнительно создаётся `target/specialist_mx.exe` через launch4j.

`-DskipTests` указан намеренно: в `pom.xml` нет surefire, а Maven подключает его по умолчанию
и падает в офлайне на `surefire-junit3`. Тестовые классы при этом всё равно компилируются —
запускать их нужно вручную.

## Запуск

```bash
java -jar target/specialist_mx-2.0.0.jar
```

Каталог приложения — текущий рабочий каталог (из него читается `specialist_mx.ini`, в нём ищется
каталог `mon` с MON-файлами).

## Проверки процессоров

JUnit-тесты и офлайн-проверки лежат в `src/test/java`:

| Класс            | Что проверяет                                                         |
|------------------|-----------------------------------------------------------------------|
| `CpuI8080Test`   | `8080PRE`, `TST8080`, `CPUTEST`, `8080EXER` через CP/M-эмуляцию BDOS  |
| `CpuZ80Test`     | `zexdoc`, `zexall`, `z80type` через ту же CP/M-эмуляцию               |
| `CPUZ80SelfTest` | Точечные сценарии `CpuZ80`: флаги, префиксы, регистры, ловушки        |
| `DisAsmSelfTest` | Оба дизассемблера: длины, тексты, заполнение буфера таблицы отладчика |

`CPUZ80SelfTest` и `DisAsmSelfTest` — обычные `main`-классы, а не JUnit:

```bash
java -cp target/classes:target/test-classes:<зависимости> \
     ru.avsh.specialist.mx.units.CPUZ80SelfTest
java -cp target/classes:target/test-classes:<зависимости> \
     ru.avsh.specialist.mx.gui.swing.debugger.disasm.DisAsmSelfTest
```

`CpuZ80Test` содержит два тяжёлых теста (`zexdoc`, `zexall`) — около 20 минут каждый; тайм-аут
в тесте выставлен на 40 минут.

Итоговая приёмка — ручной прогон эмулятора: экран, клавиатура, диск, отладчик. Никакая
автоматическая проверка не заменяет этот прогон.
